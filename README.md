# NavIC Pulse
**Live demo:** https://navic-pulse.vercel.app
NavIC Pulse watches the rubidium atomic clocks on NavIC navigation satellites
and flags a degrading clock from its ground-segment telemetry. It trains an
autoencoder on healthy satellites only, scores every 30-day telemetry window by
reconstruction error, and confirms a fault with CUSUM only once the alarm has
persisted for 60 consecutive windows. For each confirmed fault it projects
remaining useful life from the decline in clock signal level, and a static
React interface presents the results.

## Synthetic data

**Every telemetry value in this repository is synthetic.** Real NavIC internal
clock telemetry is not publicly released, so none is used here.

- The telemetry is generated by `generate_telemetry.py` from published ISRO
  iRAFS (Indian Rubidium Atomic Frequency Standard) specifications: drift,
  Allan deviation, temperature coefficient, and the measured magnitudes of
  on-orbit failure signatures (Bandi & Arora, ICG-14, 2019). The
  noise-increase signature has no published magnitude, so its factor is a
  placeholder.
- The orbital and specification references are real: satellite names, launch
  dates, GEO/IGSO assignments and the iRAFS figures come from the public
  record.
- Which satellites carry faults, and when those faults start, is a modelling
  choice. Nothing on screen describes the actual health of any real satellite.

The interface repeats this on every screen.

## What the results show

- **Earlier than fixed-limit monitoring, by a mean of 9.4 days.** CUSUM on the
  autoencoder score confirms sustained degradation a mean 9.4 days earlier
  than a fixed-limit baseline on the raw telemetry channels (limits at
  mean ± 3σ from the healthy satellites, same 60-window persistence rule). It
  is earlier on 4 of the 5 injected faults, and **1 day later on IRNSS-1G**.
- **Never before onset.** Both detectors confirm after fault onset, never
  before. This is earlier detection than the baseline, not advance warning of
  a fault that has not started.
- **The imported vs indigenous clock comparison is inconclusive.** Across the
  healthy satellites the two populations' mean reconstruction errors are
  0.22% apart. Every faulted satellite carries an imported clock, so an
  all-satellite comparison would measure fault assignment, not clock quality.

| satellite | profile | fixed-limit baseline confirms (window) | CUSUM confirms (window) | lead (days) |
|---|---|---|---|---|
| IRNSS-1E | sudden jump | 2101 | 2079 | +22 |
| IRNSS-1D | degraded | 890 | 878 | +12 |
| IRNSS-1A | noise increase | 2346 | 2335 | +11 |
| IRNSS-1I | slow drift | 1739 | 1736 | +3 |
| IRNSS-1G | degraded | 382 | 383 | −1 |

Positive lead means CUSUM confirmed first. Neither detector confirms on any of
the five healthy satellites.

### Two lead-time figures, two baselines

This repository reports two mean lead times. They measure CUSUM against
different baselines, so they are not meant to agree:

| mean lead | CUSUM compared against | source |
|---|---|---|
| **9.4 days** | the fixed-limit baseline on raw telemetry channels (mean ± 3σ from healthy satellites) | `baseline_ool.json` |
| **9.2 days** | the static threshold (0.498) on the same autoencoder score | `summary.json` |

The 9.4-day figure is the one quoted in the interface and the pitch, because a
fixed limit on raw channels is what operator out-of-limits (OOL) monitoring
actually does. The 9.2-day figure isolates what CUSUM adds over a plain
threshold on the model's own score; see [Known limitations](#known-limitations).

## Repository layout

The Python pipeline lives at the repository root; the React frontend lives in
`frontend/`.

## Running the pipeline

```bash
python config.py              # print every constant as a table (no side effects)

python generate_telemetry.py  # -> telemetry.csv          (29,000 rows, 10 satellites x 2,900 days)
python plot_raw.py            # -> demo/raw_check.png     (optional sanity check)
python preprocess.py          # -> preprocessed.npz, window_metadata.csv, scaler.joblib
python train_model.py         # -> scores.csv, model.joblib
python detect.py              # -> detections.csv
python rul.py                 # -> rul.json
python validate.py            # -> summary.json
python navic_recalibrate.py   # -> navic_recalibration.json
python make_plots.py          # -> demo/*.png            (run last of these)
```

Every stage is deterministic given `RANDOM_SEED` in `config.py`, so the
generated CSVs, arrays and model are reproducible and are not tracked in git.
On a fresh clone, run the pipeline before anything that reads its outputs.

Run `make_plots.py` after `train_model.py`: both write
`demo/score_histogram.png` from the same scores, and whichever runs later wins.

## Regenerating the frontend fixture

After the pipeline has run:

```bash
python baseline_ool.py        # -> baseline_ool.json
python export_demo_run.py     # -> frontend/public/demo-run.json, frontend/public/sample-batch.csv
```

`export_demo_run.py` is a formatter, not an analysis step. It re-scores
`preprocessed.npz` with the frozen `model.joblib` only to split each window's
error across channels, and it stops if the re-scored errors do not match
`detections.csv` or if `navic_recalibration.json` does not reproduce the
alarms. `generated_at` is taken from the modification time of `summary.json`,
so re-running the export against unchanged outputs produces a byte-identical
file.

**Keep `frontend/src/Pipeline.jsx` in sync.** It hardcodes the static threshold
(0.498), the autoencoder shape (150-64-12-64-150), the 60-window persistence
rule and the ±3σ baseline limits, because the stage list renders even before
the run loads. Recalibrating the pipeline means updating that file too.

## Deployment

The frontend deploys to Vercel as a static site.

| setting | value |
|---|---|
| Root Directory | `frontend` |
| Framework Preset | Vite |
| Build Command | `npm run build` |
| Output Directory | `dist` |

`frontend/vercel.json` already sets the framework, build command and output
directory; the Root Directory must be set in the Vercel project settings.

There is no backend and no serverless function. The app is fully static: it
fetches `public/demo-run.json` (served as `/demo-run.json`) and, from the
Upload screen, `public/sample-batch.csv`. The Upload screen validates a file
entirely in the browser; it does not send it anywhere and does not run the
model. The app has no client-side routes, so no rewrites are needed.

## Why it is built this way

The design choices that matter are the ones made against a first instinct:

- **Trained on healthy units only.** Faulted satellites are excluded from the
  scaler fit and the training set, so their telemetry falls outside the healthy
  distribution by construction rather than by tuning.
- **A detection must persist.** A single-window alarm at a 1% false-alarm rate
  fires on a *healthy* clock by day 60–429 purely by chance. Requiring 60
  consecutive alarm windows is what makes the lead times real: healthy units
  then never fire at all.
- **The baseline is a fixed limit on raw channels.** Operator ground segments
  watch raw housekeeping telemetry against fixed limits, not a model's score,
  so that is what "earlier" is measured against. The limits come from the
  healthy satellites' observed distributions, not the iRAFS 5e-13/day drift
  figure, which does not apply to a steered residual.
- **Every fault is on an imported clock.** A failing indigenous satellite would
  contaminate the imported vs indigenous comparison. The comparison is
  therefore computed over healthy satellites only, where it is inconclusive.
- **Remaining life is projected from signal level, not drift rate.** The iRAFS
  5e-13/day figure is a *free-running* specification, while `freq_offset_y`
  here is a steered ground-segment residual — the two are not commensurate, and
  90-day drift slopes are dominated by random-walk noise. `rafs_signal_level`
  is a genuine wear curve and leads the frequency fault by ~60 days.

## Detection metrics

| metric | value |
|---|---|
| ROC AUC (threshold-free) | 1.0000 |
| Precision / Recall / F1 (CUSUM, sustained) | 1.0000 / 0.9920 / 0.9960 |
| Precision / Recall / F1 (threshold, sustained) | 1.0000 / 0.9854 / 0.9927 |
| False positives across 21,710 healthy windows | 0 |
| Faults caught | 5 / 5 |
| Healthy units falsely flagged | 0 / 5 |
| Detection latency after onset | 7–15 days, on ramps of 100–300 days |

The remaining 56 missed windows are detection *latency*, not missed faults: the
60 windows a detection must accumulate are scored as misses even though every
fault is eventually caught.

These figures supersede an earlier ROC AUC of 0.9348 and recall of 0.8425. Two
calibration changes account for the difference, neither of them a model change —
the autoencoder and its seed are untouched:

  * **Labels are now scored from each satellite's own `anomaly_start_day`.** The
    two `degraded` units were previously labelled anomalous across their whole
    record, because the generator multiplies their drift from day 0 and treats
    `anomaly_start_day` as the knee where they worsen. That is still true of the
    generator, but those 1,242 early windows score 0.160 against the healthy
    fleet's 0.148 — indistinguishable — and they made up 100% of the pipeline's
    false negatives. The old recall was measuring the labelling, not the
    detector. See `preprocess.py`.
  * **`K_SIGMA` moved from 3 to 8.** The healthy score distribution is
    right-skewed, with a maximum 6.5σ above its own mean, so the 3σ bar sat
    inside the healthy tail. See `config.py` and `navic_recalibrate.py`.

Remaining useful life, projected at detection + 30 days:

| satellite | profile | RUL (days) |
|---|---|---|
| IRNSS-1G | degraded | 50 ± 2 |
| IRNSS-1D | degraded | 53 ± 2 |
| IRNSS-1I | slow drift | 93 ± 3 |
| IRNSS-1A | noise increase | 151 ± 6 |
| IRNSS-1E | sudden jump | 208 ± 8 |
| 5 healthy units | — | no finite RUL |

## Known limitations

These are real and worth stating rather than discovering in a demo:

- **The dataset is synthetic.** See [Synthetic data](#synthetic-data).
- **The RUL error bars are model-fit precision, not accuracy.** The generated
  signal decline plateaus near 0.91 and never actually reaches the 0.85 failure
  limit, so every RUL extrapolates a decline that stops. The figure answers
  "if the current rate continued, when would it cross" — the honest question a
  linear projection can answer.
- **`CUSUM_PERSISTENCE = 60` is fitted to five healthy satellites.** It is the
  point where healthy units go quiet on *this* dataset, which is demo-grade
  calibration, not an operationally justified constant.
- **The lead over the fixed-limit baseline on raw channels is modest and
  uneven.** Against that baseline (`baseline_ool.json`), CUSUM confirms a mean
  of 9.4 days earlier, ranging from −1 to +22, on five faults. Both detectors
  key on the same signal: every baseline confirmation is triggered by
  `rafs_signal_level`.
- **CUSUM's gain over the static threshold on the autoencoder score is small.**
  Against that baseline (`summary.json`), with matched persistence, CUSUM
  confirms 2–16 days earlier, a mean of 9.2 days. This is a different
  comparison from the 9.4-day figure above. The accumulation helps least where
  per-window scores are already separable.
- **Severity bands are effectively satellite-level.** The 60th-percentile split
  lands on the degraded/non-degraded boundary, so "Critical" means "this is a
  degraded unit" rather than grading severity within one satellite's history.
- **The secondary RUL indicator does not work.** `steering_correction_ns` is
  too noisy at a 90-day window to fit a trend; it is scaffolding, not a result.
